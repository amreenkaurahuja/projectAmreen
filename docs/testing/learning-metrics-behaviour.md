## 2. What "verified" means here

Every row above marked with an end-to-end test (`learning-metrics-end-to-end*.test.tsx`) was checked by running the **real** application code — the actual `QuestionExplainerFlow` component, the actual `httpLearningEventPublisher`, the actual `POST /api/v1/learning-events` route handler (including its Zod validation and error mapping), the actual `LearningEventDeliveryService`, and the actual `SupabaseLearningEventRepository` / `SupabaseQuestionExplainerMetricsRepository` / `calculateQuestionExplainerMetrics`. The only faked component is the database and network transport (`tests/unit/helpers/fake-learning-events-supabase.ts`, an in-memory stand-in for the `learning_events` table plus a fetch interceptor that hands the request to the real route handler). This means a defect in how any of these pieces integrate — column-name drift, a mapping bug between the write and read repositories, a schema/type mismatch — would have surfaced as a test failure. None did.

## 3. Feature-flag expectations

- `NEXT_PUBLIC_QUESTION_EXPLAINER_METRICS_ENABLED` is read once, at module load, by `default-learning-event-publisher.ts` — not re-evaluated per render or per request.
- Disabled (absent, empty, or any value other than the exact string `"true"`): `QuestionExplainerFlow`'s default publisher is the no-op; zero requests to `/api/v1/learning-events`; educational behaviour is identical to the pre-Stage-6.1 component.
- Enabled: the default publisher is the real HTTP publisher; every educational transition fires exactly one delivery attempt.
- In both states, an explicitly supplied `publisher` prop overrides the flag-selected default — the flag only decides what an _unwired_ caller gets.
- The flag is a build-time-inlined `NEXT_PUBLIC_*` variable (documented in `docs/ENVIRONMENTS.md`) — changing it in a deployed environment requires a rebuild, not just a config toggle.

## 4. Best-effort delivery semantics (what reporting must tolerate)

These are not defects — they are the direct, intentional consequence of "one delivery attempt, no retry, no queue" (TDS-008 §10):

- An `explanation_opened` row can be missing even though later events in the same session (`step_viewed`, a terminal event) were persisted, and vice versa — each event's delivery succeeds or fails independently.
- Intermediate `step_viewed` rows can be missing without anything reconstructing them.
- `stepProgression` for a given step is **not** guaranteed to be ≤ `explanationsOpened` — a session's `step_viewed` row can exist without its `explanation_opened` row ever having been persisted. Verified explicitly in `learning-metrics-invariants.test.ts` rather than left as an unstated assumption.
- `completionRate`/`abandonmentRate` are not guaranteed to be ≤ 1 — more terminal events can be observed than opened events in a window. This is treated as truthful evidence of incomplete delivery, never clamped.
- A single `attempt_id` can have multiple legitimate `session_id`s (the learner reopening the same explanation).
- `occurred_at` is client-supplied and only syntax-validated — a skewed browser clock is accepted, not rejected.

## 5. Known limitations (unchanged from the Stage 6.4A audit — restated here for one place to check)

- `completion_rate`/`abandonment_rate` numerator/denominator, step-progression definition, and the duration cap were the four ambiguities the audit found in LDS-002; all four were resolved by TDS-008 §11 and are what this suite verifies. Nothing new was discovered during 6.5.
- Subsequent correctness (LDS-002 §7) remains unimplemented and out of scope for Release 0.7 — no code in this capability computes it.
- No dashboard, reporting API route, or UI exists — the read model is a library surface only (`SupabaseQuestionExplainerMetricsRepository` + `calculateQuestionExplainerMetrics`), matching TDS-008 §11.2/§15 and the Stage 6.4A audit's recommendation not to build Stage 6.4C for Release 0.7.
- Cross-learner/low-volume aggregate exposure risk (flagged in the Stage 6.4A audit §9) remains an open question for any future multi-learner reporting surface — `countUniqueLearnersUsingExplanations` exists but nothing currently calls it with real data.

## 6. Result

No architectural contradiction was found. Every contract established across Stages 6.1–6.4 held under direct, full-pipeline verification. No production code changed as a result of this stage — see the accompanying PR for the complete list of test-only files added.
